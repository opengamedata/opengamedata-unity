# OGD Replay — input capture channel (experiment)

Branch: `replay-experiment`. Experimental; not referenced by any shipping scene.

## What this is

Capture of **player input** for replay: pointer motion sampled at a fixed
cadence (10 Hz by default) plus discrete button/key/scroll/action events at
their true times. This is the piece the replay system did not have — the
existing capture packages record game-object state, not input.

Two channels, deliberately not mixed:

- **Sampled** pointer motion — fixed cadence, quantized to an absolute integer
  grid in a declared reference space. Coordinates are absolute, never deltas,
  so a viewer can seek to any time without replaying from zero. A sample is
  emitted only when the quantized value actually changed, so a still pointer
  costs zero bytes.
- **Discrete** events — button/key transitions, scroll, and semantic UI actions,
  stamped at the time observed and never thinned to the cadence. A click that
  lands between two samples still happened.

A resize emits a `space` event and invalidates the held position; earlier
coordinates are *not* rescaled, because they were true in the old space.

Semantic `action` events are recorded alongside raw coordinates on purpose:
raw pixels do not survive a layout change, and the pair is what keeps an old
recording interpretable.

## Files

- `Runtime/ObserveInput.cs` — `ObserveInputRecorder`, the encoder. Owns no
  clock and no `Input` polling; the caller supplies observed values and a
  monotonic session time. That is what makes cadence and encoding testable
  off-device.
- `Runtime/ObserveInputCapture.cs` — `ObserveInputCapture`, the Unity
  `MonoBehaviour` that owns the clock and polls `Input`. Assign `sink` to
  receive encoded lines; call `RecordAction(target, action)` from game code.
- `Tools~/input-codec/input.mjs` — decoder/analyser: strict `decode`,
  `pointerAt`, `buttonsAt`, `verifyCadence`, `cost`, `peakWindow`.
- `Tools~/input-codec/input.test.mjs` — the test suite (11 tests).
- `Tools~/input-codec/fixture.json` — generated by the real C# recorder.
- `Tools~/conformance/` — the harness that drives the recorder to emit the
  fixture.

`Tools~` has a trailing tilde, so Unity ignores it: the Node and SDK code is
never imported as assets or compiled into a player build.

## Wire format (schema 1)

```
input_header  {kind,schema,intervalMs,precision,space:{w,h}}
pointer       {t,sequence,kind,x,y,inside}      absolute quantized grid coords
button        {t,sequence,kind,device,button,down}
scroll        {t,sequence,kind,dx,dy}
action        {t,sequence,kind,target,action}
space         {t,sequence,kind,w,h}
```

`sequence` is contiguous and `t` non-decreasing; `decode` enforces both, so a
truncated or reordered upload fails loudly instead of yielding a plausible
replay. An unknown `schema` is refused rather than guessed at.

## Verifying

The fixture is generated by the **real** `ObserveInputRecorder.cs`, not written
by hand — otherwise the tests would only prove the decoder agrees with itself.
Both halves run in containers; neither needs a Unity license.

```sh
# 1. generate fixture.json from the real C# recorder (also checks its guards)
docker run --rm -v rxwork:/src -w /src -e OUT_DIR=/src -e HOME=/tmp \
  mcr.microsoft.com/dotnet/sdk:8.0-alpine dotnet run --project harness.csproj

# 2. decode and assert against it
docker run --rm -v rxwork:/src -w /src node:20-alpine node --test input.test.mjs
```

Last run: `events=34 guards_enforced=5/5`, then **11/11 tests pass**.

Measured on that fixture (3.7 s of continuous play with sweeps, clicks, a key,
a resize and a 600 ms idle window):

- 2555 B total → **5.52 kbps per client**
- worst 1 s window **7.10 kbps** → **142 kbps for 20 concurrent clients**
- 24 pointer samples, minimum gap 112 ms (never below the 100 ms cadence floor)
- 0 samples across the 600 ms still-pointer window

The 20-client figure is the number that matters for a live classroom wall; the
test fails if it ever exceeds 2 Mbps.
