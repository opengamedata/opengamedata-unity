# Observe-input capture: generalization strategy

Scope: how input capture ports from Locke's Gambit to the rest of the OGD
fleet. Grounded in a survey of the four pilots, not in general principle —
what I found is below, and it rules some obvious designs out.

## What the fleet actually looks like

| | wake | bloom | hercules | lockes-gambit |
|---|---|---|---|---|
| Unity | 2019.4.40f1 | 2021.3.40f1 | 2022.3.47f1 | 2022.3.62f3 |
| `FieldDay.Core` | **no** | yes | yes | yes |
| `InputMgr.cs` | — | 323 ln | 488 ln | 619 ln |
| legacy `Input.*` | yes | yes | yes | yes |
| `UnityEngine.InputSystem` | 0 | 0 | 0 | 0 |
| touch | 0 | 0 | 0 | 0 |
| `PointerEventData` files | 10 | 12 | 9 | 11 |
| `OGDLog` | yes | yes | yes | yes |

Five facts that decide the design:

1. **Nobody uses the new Input System, and nobody uses touch.** Building an
   abstraction over both input backends would be scaffolding for a case that
   does not exist. Target legacy `Input` and keep the seam narrow enough to
   add a backend later.
2. **Unity spans 2019.4 → 2022.3.** Anything newer than 2019.4 in the capture
   path breaks wake. This already bit me: `realtimeSinceStartupAsDouble` is
   2020.2+, fixed in `85eb744`.
3. **`InputMgr` is vendored per-game and has diverged** — 323 / 488 / 619
   lines, three distinct hashes. It looks like the natural integration point
   and is a trap: binding to it means three bindings that drift.
4. **Wake has no `FieldDay.Core` at all.** Any plan that assumes the shared
   framework excludes the oldest and largest pilot.
5. **`OGDLog` is the only dependency all four already share**, and every game
   emits semantic events through it (`NewEvent("open_bestiary")`,
   `"switch_job"`, `"toggle_map_mode"`…).

→ **Bind to `OGDLog`, never to `InputMgr`.** The common denominator is the
logger, not the input layer.

## The strategy

### 1. Three layers, one of them per-game

- **Encoder** (`ObserveInputRecorder`) — no clock, no `Input`, no Unity. Pure
  value-in/bytes-out. Portable by construction and testable off-device, which
  is what lets the conformance suite run in a container with no Unity seat.
- **Driver** (`ObserveInputCapture`) — owns the clock and polls legacy `Input`.
  The only file that touches `UnityEngine`. Ships once, unchanged, to all four.
- **Binding** (per game, ~10 lines) — assigns `sink` and calls
  `RecordAction(target, action)`. The only part a game author writes.

The cost of onboarding a game is layer 3 alone. Nothing in layers 1–2 is
allowed to know a game's name.

### 2. Ship via the existing optional-dependency idiom

The house pattern is already there — `FieldDay.Core.asmdef` carries:

```json
{ "name": "com.fieldday.opengamedata-unity", "expression": "1.0.6",
  "define": "USING_OGDLOG" }
```

…and `OGDExtensions.cs` wraps its whole body in `#if USING_OGDLOG`. The fleet
uses `USING_BEAUUTIL`, `USING_URP`, `USING_XR` the same way (200/76/64 files).

Replay capture should follow it exactly: `versionDefines` → `USING_OGDREPLAY`,
and the driver guarded by it. A game without the package compiles with capture
absent rather than broken, so wake can adopt on its own schedule.

### 3. Semantic actions are the portable payload; coordinates are not

Raw pixels do not survive a layout change, a resolution change, or a UI
revision — a 2024 recording replayed against a 2026 build points at the wrong
things. Coordinates are only interpretable alongside the semantic action.

The fleet already names its events in `snake_case` through `OGDLog`. Capture
should reuse those names rather than invent a parallel vocabulary, so analysis
joins cleanly against existing telemetry. Per-game work is tagging the handlers
a researcher cares about; `PointerEventData` is in 9–12 files per game, so the
realistic surface is tens of call sites, not hundreds.

### 4. Per-game cost, honestly

- **lockes-gambit, hercules, bloom** — driver drops in; binding plus action
  tagging. Days, not weeks.
- **wake** — no `FieldDay.Core`, and 2019.4. The driver compiles there now
  (verified), but the float clock degrades after hours of uptime, and wake
  vendors OGD at `Assets/Plugins/OpenGameData` rather than UPM, so
  `versionDefines` won't auto-fire; it needs a manual define. Treat wake as a
  second milestone, not part of the first.

### 5. Keep the conformance suite as the anti-drift mechanism

The fixture is generated by the real C# encoder and consumed by the JS decoder,
so the recording and analysis halves cannot diverge silently. A hand-written
fixture would only prove the decoder agrees with itself. Every new game inherits
this for free; every format change has to pass it.

## What I'd defer

- **New Input System / touch support** — zero current usage. Add when a game
  needs it.
- **Gameplay-state capture** — already handled by the replay packages. Input
  capture should not grow into a second state recorder.
- **Per-game codecs** — bandwidth is 5.52 kbps/client, 142 kbps at 20 clients
  against a 1.0 Mbps ceiling. Input is not the budget problem; there is nothing
  to optimize yet.

## Recommended sequence

1. Add `USING_OGDREPLAY` via `versionDefines` + guard the driver.
2. Wire `sink` into `OGDLog`'s upload path once, in the OGD client.
3. Bind Locke's Gambit as the reference integration; tag its actions.
4. Port to hercules and bloom (same framework, should be near-free).
5. Replay-mode player, then the video wall.
6. Wake last, as its own milestone.

Steps 1–2 are mine. Step 3's action list is a judgement call about what
researchers want to see and is worth ten minutes of your time; 4–6 follow
mechanically once 3 settles.
